# Press & Sport — persistent reservation design

Status: **design only; not deployed**. The SQL in `sql/presssport_publication_reservations.sql` is not connected to a live database.

The existing GitHub JSON ledger is a read-only audit aid, **not** a lock. A production publisher must acquire a durable reservation with a single database INSERT before contacting Meta. The unique primary key is the deterministic `publication_key` generated by `scripts/publication_ledger_state.py` from the account and ordered media URLs. Competing workers attempting the same key must fail, never overwrite or silently ignore the conflict.

The reservation should be created only after validating the exact manifest SHA-256, separate recent user authorization, account identity, and editorial readiness. Keep the key reserved through `publishing`, `published`, and `uncertain`. Do **not** automatically release the key on network timeouts, GitHub job cancellation, or ambiguous Meta responses. Reconcile uncertain results against the Meta account before a human-authorized decision.

Store database credentials exclusively as server-side secrets. Never expose the service key in a public frontend or logs. Use a dedicated Press & Sport project rather than repurposing unrelated databases. Run schema and security reviews before deployment. This design does not implement the publishing API or prove end-to-end idempotency.
